# SMC 프로토타입(MoorSMCProbe) 실측 기록

이슈: #5

## 결론 (3단계 실측 종료, 2026-11-16)

대상은 기기 한 대(MacBookAir10,1, Apple M1, macOS 13.5.2)다. 아래 "확인"은 이 기기에서 소유자가 직접 실행해 관찰한 것이고, 다른 기기나 macOS 버전에서도 같다는 뜻이 아니다.

### 확인된 것

키 값:
- `CH0B` ← `02`를 쓰면 쌍이 `02`/`02`가 되고 충전이 차단된다.
- `CH0C` ← `02`를 쓰면(`CH0B`는 `00`) 쌍이 `01`/`01`이 되고, 이때도 충전이 차단된다.
- 두 키에 차례로 `02`를 쓰면 `03`/`03`이 된다.
- 복구는 `CH0B`와 `CH0C`를 모두 `00`으로 써야 `00`/`00`이 된다.

충전 상태 반영 지연:
- 충전 상태는 키 값이 바뀐 뒤 늦게 따라온다. 차단은 38~50초, 해제는 약 42초 걸렸다.

복구 동작:
- `--revert-after` 중 SIGINT(Ctrl-C)를 받으면 복구하고 종료 코드 130으로 끝난다.
- `--revert-after` 시간이 지나면 복구한다.
- 옵션 없이 `disable-charging`을 실행하면 프로그램이 끝난 뒤에도 값이 유지된다.

### 가설

- 두 키가 비트 `0x02`(`CH0B`)와 `0x01`(`CH0C`)로 합쳐져 같은 값으로 읽힌다는 모델. 위 관찰과는 모두 맞지만 펌웨어 동작으로 확인된 사실은 아니다.

### 미확인

- SIGTERM과 SIGHUP을 받았을 때의 복구 (코드와 유닛테스트는 있으나 실측하지 않음)
- `03`/`03`에서의 충전 상태
- 재부팅 후의 값
- 잠자기 후의 값

## 소스에서 확인한 충전 제어 키 (Apple Silicon)

| 키 | 용도 | 허용 값 | 차단 값 | 크기 |
|---|---|---|---|---|
| `CH0B` | 충전 제어 1 | `00` | `02` | 1바이트 |
| `CH0C` | 충전 제어 2 | `00` | `02` | 1바이트 |

- batt는 두 키가 모두 있으면 `CH0B` → `CH0C` 순서로 둘 다 쓰고, 충전 허용 여부는 `CH0B == 00`으로 판정한다.
- `CHTE`(4바이트)는 batt에서 `CH0B`/`CH0C`가 없을 때 쓰는 키다. Moor는 쓰지 않는다.
- `CH0I`/`CH0J`는 어댑터 차단(강제 방전) 키로, 이 프로토타입의 범위 밖이다.

## 실측 환경

- 기기: MacBookAir10,1 (Apple M1)
- macOS: 13.5.2

## 읽기 결과

### 2026-11-15, sudo 없이 실행 (Claude Code가 실행)

```
$ .build/debug/MoorSMCProbe read CH0B CH0C
CH0B  [hex_]  1 byte(s)  01
CH0C  [hex_]  1 byte(s)  01

$ .build/debug/MoorSMCProbe read BUIC CHTE CH0I
BUIC  [ui8 ]  1 byte(s)  39
CHTE  [ui32]  4 byte(s)  00 00 00 00
CH0I  [ui8 ]  1 byte(s)  00
```

- 읽기는 root 권한 없이 된다.
- `BUIC` = 0x39 = 57로, 같은 시각 `ioreg`의 `CurrentCapacity` 57과 일치한다.
- 당시 상태: 전원 연결됨, 57%, 충전 안 함(`pmset -g batt`: "AC attached; not charging").
- **`CH0B`/`CH0C`가 소스에서 확인한 `00`/`02`가 아닌 `01`이었다.** 이때 AlDente(앱과 권한 헬퍼)가 실행 중이었으므로 AlDente가 쓴 값일 가능성이 있다. `01`의 의미는 확인하지 못했다.
- `CHTE`가 macOS 13.5.2에도 존재한다(값 `00 00 00 00`).

### 소유자 직접 확인 (2026-11-16)

- `CH0B`, `CH0C`는 각각 1바이트다.
- `02`/`02`일 때 충전이 멈추고, `00`/`00`일 때 충전이 재개된다.
- 위 값은 AlDente가 쓴 값을 `read`로 관찰한 것이다. MoorSMCProbe로 직접 쓴 결과는 아래 "쓰기 결과"에 기록한다.
- `01`의 의미는 확인하지 못했다. MoorSMCProbe는 `01`을 "알 수 없음"으로 경고만 하고 쓰기는 계속 진행한다.

## 쓰기 명령

화이트리스트는 키 2개(`CH0B`, `CH0C`) × 값 2개(`00`, `02`)뿐이다. 임의 키에 쓰는 명령은 없다.

| 명령 | 동작 |
|---|---|
| `enable-charging` | `CH0B`와 `CH0C`에 모두 `00`을 쓰고 쌍이 `00`/`00`이 될 때까지 폴링한다. 한 키의 쓰기가 실패해도 나머지 키는 쓴다. |
| `disable-charging` | `CH0B`에만 `02`를 쓰고 쌍이 `02`/`02`가 될 때까지 폴링한다. 실패하면 두 키를 `00`으로 되돌린다. |
| `disable-charging --revert-after <초>` | 위와 같이 쓴 뒤, 시간이 지나거나 SIGINT/SIGTERM/SIGHUP을 받으면 두 키를 `00`으로 복구한다. |
| `set <B값> <C값\|-> [--order bc\|cb] --hold <초>` | 실험용. 지정한 값을 쓰고 유지 시간 동안 값을 출력한 뒤 두 키를 `00`으로 복구한다. 쓴 값을 검증하지 않는다. |
| `watch --seconds <초>` | 읽기 전용. 두 키를 200ms마다 읽어 출력한다. sudo가 필요 없다. |

공통 동작:
- root가 아니면 쓰기 명령은 SMC를 열기 전에 종료한다.
- 쓰기 전에 두 키가 모두 있고 1바이트인지 확인하고, 현재 쌍과 그 해석을 출력한다.
- 검증은 항상 쌍 단위다. 100ms 간격으로 최대 2초까지 두 키를 함께 읽고, 쌍의 변화 순서를 `읽기 변화 CH0B/CH0C: 00/00 (0ms) → 02/02 (300ms)` 형식으로 출력한다. 키 하나를 쓴 직후의 값은 검증하지 않는다.
- **검증은 키 값만 본다. 실제로 충전이 멈췄는지, 재개됐는지는 판단하지 않는다.**

쌍의 해석(키 값에 대한 설명이며 충전 상태를 뜻하지 않는다):

| 쌍 | 출력 문구 |
|---|---|
| `00`/`00` | 차단 값 없음 |
| `02`/`02` | CH0B 차단 값만 설정됨 |
| `01`/`01` | CH0C 차단 값만 설정됨 |
| `03`/`03` | CH0B, CH0C 차단 값 모두 설정됨 |
| 그 외 | 알려지지 않은 조합 (경고) |

종료 코드: 성공 0, 실패 1, 사용법 오류 2, 시그널로 끝나 복구한 경우 128+시그널 번호(Ctrl-C는 130).

한계:
- `--revert-after` 없이 `disable-charging`을 실행하면 `02` 값은 `enable-charging`을 실행할 때까지 남는다.
- SIGKILL(`kill -9`)이나 강제 종료로는 복구가 실행되지 않는다. 이 경우 `enable-charging`을 직접 실행한다.
- 시작 쌍이 `01`/`01`이나 `03`/`03`이면 `disable-charging`은 `03`/`03`이 되어 `02`/`02` 검증에 실패하고, 두 키를 `00`으로 되돌린 뒤 실패로 끝난다. 다시 실행하면 `00`/`00`에서 시작한다.
- AlDente 같은 다른 충전 제한 도구가 실행 중이면 값을 다시 덮어쓸 수 있다. 실측은 그 도구를 완전히 종료하고 한다.

## 쓰기 결과

### 2026-11-16, 1차 (쓰기 직후 한 번만 읽어 검증하던 버전, 소유자 실행)

`disable-charging`이 8번 모두 같은 지점에서 실패했다. AlDente 헬퍼는 등록만 돼 있고 프로세스는 돌지 않는 상태였다.

| 단계 | 쓴 값 | 직후 읽힌 값 |
|---|---|---|
| `CH0B` ← `02` | `02` | `02` (통과) |
| `CH0C` ← `02` | `02` | `03` (검증 실패) |
| 롤백 `CH0B` ← `00` | `00` | `01` |

- 다음 실행은 항상 `00`/`00`에서 시작했다. `03`과 `01`은 쓰기 직후에만 보이는 일시적인 값으로 보인다.
- 확인하지 못한 것: 일시적인 값이 얼마나 지속되는지, 값이 자리 잡은 뒤 실제로 충전이 멈추는지, `01`/`03`의 의미.
- 이 결과 때문에 검증을 폴링 방식으로 바꾸고 `watch`를 추가했다.

### 2026-11-16, 2차 (폴링 검증 버전과 `watch`, 소유자 실행)

- `CH0B`와 `CH0C`는 항상 같은 값으로 읽힌다.
- `CH0B` ← `02` 뒤에는 `02`. 이어서 `CH0C` ← `02`를 쓰면 `03`이 되고, 2초 동안 그대로다(일시적인 값이 아니다).
- 롤백에서 `CH0B` ← `00`만 쓴 상태에서는 `01`이 남고, `CH0C` ← `00`까지 써야 `00`이 된다.
- AlDente가 만든 차단 상태는 `02`/`02`였다.
- 따라서 키를 하나 쓸 때마다 그 키만 검증하는 방식은 오보를 낸다. 복구와 `enable-charging`은 두 키를 모두 쓴 뒤 쌍(`00`/`00`)을 검증하도록 바꿨다.

### 2026-11-16, 3차 (`set` 실험, 소유자 실행)

| 쓴 내용 | 읽힌 쌍 | 충전 |
|---|---|---|
| `CH0B` ← `02` | `02`/`02` | 멈춤 |
| `CH0C` ← `02` (`CH0B`는 `00`) | `01`/`01` | 멈춤 |
| 두 키에 차례로 `02` | `03`/`03` | 미확인 |
| `03`/`03`에서 `CH0B` ← `00` | `01`/`01` | |
| 이어서 `CH0C` ← `00` | `00`/`00` | |

- 두 키는 읽을 때 항상 같은 값으로 보였다.
- 충전 중단은 쓴 뒤 38~50초, 충전 재개는 약 42초 뒤에 반영됐다.

이 결과에 따라 `disable-charging`은 `CH0B`에만 `02`를 쓰도록, `enable-charging`과 모든 롤백은 두 키에 `00`을 쓰고 쌍을 검증하도록 바꿨다.


### 2026-11-16, 4차 (`CH0B`만 쓰는 `disable-charging`, 소유자 실행)

- SIGINT 복구(종료 코드 130), 시간 만료 복구를 확인했다.
- 옵션 없는 차단은 프로그램 종료 뒤에도 값이 유지됐다.
- 충전 상태 반영은 차단 38~50초, 해제 약 42초였다.
- SIGTERM, SIGHUP, 재부팅, 잠자기, `03`/`03`의 충전 상태는 실측하지 않았다.

## 가설이 코드에 반영된 범위

비트 모델(문서 맨 위 "가설")을 따르는 부분:
- `disable-charging`이 `CH0B`만 쓰는 것
- 쌍 해석 문구(`02`/`02`는 "CH0B 차단 값만 설정됨" 등)
- 테스트용 가짜 SMC(`SharedRegisterSMC`)의 동작

가설과 무관한 부분:
- 쓰기 검증은 쓴 뒤 읽힌 쌍이 기대값(`02`/`02` 또는 `00`/`00`)인지만 본다. 충전 상태는 판단하지 않고, 반영 지연을 기다리지도 않는다.

비트 모델에서 따라 나오는 해석(가설): AlDente가 만든 `02`/`02`는 `CH0B`에만 `02`를 쓴 결과이고, 2026-11-15에 본 `01`/`01`은 `CH0C` 쪽만 켜진 상태다.

반영 지연 때문에 주의할 점: `--revert-after`나 `--hold`가 40~50초보다 짧으면 충전이 멈추기 전에 복구되어 `pmset -g batt`에 변화가 보이지 않을 수 있다.
